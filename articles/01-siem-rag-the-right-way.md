# 给一个自治 Agent 的两万次工具调用做安全分析台：RAG 在 SIEM 场景的正确姿势

> 本文所有数据均为**脱敏后的聚合统计**：不含真实用户名、主机路径、内网域名/IP 或邮箱；
> 引用的事件一律改写为示意结构。项目全程本地运行，不连公网、不做公开部署。

## 0. 先讲问题，不讲技术

一个自治编码 Agent 在沙箱里跑了几周，权限门（policy gate）把它的每一次工具调用都记成一条
审计日志：时间、工具、类别、放行/拦截、理由、参数。攒下来是 **2.2 万+ 条 JSONL**。

安全负责人想问的不是"把日志导给我"，而是三类问题：

1. **数字**：拦截率多少？越界写几起？fail-closed 几次？
2. **证据研判**：`curl` 为什么被拦？被拦之后它有没有换个法子绕过去？
3. **模式**：这一千多次拦截，主要在拦什么？有没有"代理人自作聪明"的绕行序列？

把这些问题直接丢给一个大模型 + 向量库，会得到一个**听起来很顺、但数字可能是编的、引用可能
是假的**的答案。在安全运营（SIEM/SOC）场景，这是不可接受的。

这篇文章讲我怎么用一套"**三层架构**"把它做对，以及为什么这才是 RAG 在安全分析场景的正确
姿势——而不是再做一个"爬几页文档切块问答"的套壳。

## 1. 数据形态决定切片策略：不要按长度硬切日志

普通 RAG 的 chunking（语义边界、固定 token、overlap）在这里是错的，因为语料不是文档，是
**事件流**。一条拦截的"意义"依赖它前后的行为：

```
T+0s   bash  curl https://example.com          -> deny（外联，不可回滚）
T+2s   web_fetch  https://example.com          -> deny（换了专用网络工具，同一 URL）
```

单看任何一条，你只能说"拦了一次 curl"；把前后事件放一起，才看得到**绕行意图**。所以我做了
三种语义单元（约 5,500 个文档）：

- **事件语义卡 event_card**：每条 deny/fail-closed/高风险 allow，带前 2 后 2 条上下文；
- **会话簇 event_cluster**：按 10 分钟空闲切窗，把一个工作回合聚成摘要块（约 60 个）；
- **报告块 report_chunk**：Agent 自己写的 Markdown 回合报告，按 H2 切（数量约是事件卡的
  3.4 倍）。

最后这个"3.4 倍"很关键，它会在检索阶段咬人——见第 3 节。

## 2. 三层架构：让确定的归确定，让语义的归语义

```
                 ┌─────────────────────────────────────────────┐
   用户问题 ───▶ │  Query Router（确定性规则，不额外调一次模型）   │
                 └───────────────┬─────────────────────────────┘
                    STATS        │ EVIDENCE            MIXED
              ┌──────────────────┼────────────────────────┐
              ▼                  ▼                         ▼
      受保护的只读 SQL      混合检索 + Rerank          先取数再检索
      （DuckDB 三道闸）     BM25 + BGE-M3 + RRF       两路结果合并
              │                  │                         │
              └──────────────────┴────────────┬────────────┘
                                               ▼
                              LLM 只做"带证据的语言组织"
                          （数字原样透传 / 强制引用 / 可拒答）
```

**第一层：结构化统计走 DuckDB，不走向量库，更不让模型算。**
"拦截率多少"这种问题，数据库里有一个确定答案。让 LLM 算，等于花钱请它掷骰子。这一层我做成
一个**只读 SQL 工具 + 三道安全闸**，下一篇文章细讲。

**第二层：证据研判走混合检索。** 稀疏 + 稠密 + 重排，见第 3 节。

**第三层：LLM 只负责把数字和证据组织成一句人话。** 它不生产数字、不生产 evidence_id，只
做表达和语义归因。

## 3. 检索：纯向量在安全日志上为什么不够，混合 + rerank 怎么补

### 3.1 纯稠密向量的两个失败模式

我用 BGE-M3（本地、Apple Silicon MPS 加速）做稠密向量。但纯向量在两类问题上系统性翻车：

- **抽象问法**："有没有绕过网络限制的尝试？"——真实证据是"curl 被拦→换 web_fetch→再换
  python urllib"的事件序列，语义上离这句话的向量并不近；
- **精确命令词**："chmod/sudo 提权"、"node -e fetch npm"——工具名、命令、路径、URL 是
  **精确词项**，embedding 天然不敏感。而这些词往往只出现在事件卡正文。

### 3.2 BM25 负责"字面精确"，稠密负责"语义相近"，RRF 负责不偏袒

稀疏侧我没有上 ES/Lucene，而是写了一个零依赖内存 BM25（5.5k 文档规模不需要重武器），
tokenizer 针对安全日志定制：shell 命令、flag、路径、URL 整体保留为词项，中文按 bigram 切，
事件卡正文（相对上下文区）命中加权。稠密侧走 Qdrant。

两路各取候选，用 **RRF（Reciprocal Rank Fusion，k=60）** 融合，再加一层**意图扩展**
（"绕过"→ 自动补一条 "curl web_fetch 同一 URL 换工具" 的子查询）。

### 3.3 一个真实的坑：报告块靠词频"淹没"事件卡

直接对全局 RRF 取 top-20，结果被 report_chunk 占满——因为报告块数量是事件卡的 3.4 倍，而且
长文本更容易重复问题词。真实事件卡（比如"写文件被拦"）的融合分被挤到 20 名开外。

我尝试过几种"固定类型配额"（事件至少 3 张、报告最多 2 张），都会在另一批题上此消彼长：硬
配额会丢掉 cross-encoder 打高分的跨类型证据（比如总结绕行序列的会话簇）。**最终方案是：在
每一路召回内部先做类型平衡（事件 top-N + 非事件 top-N），再过全局 RRF；重排以 reranker
打分为主，只用最小锚点防止系统性偏差**（精确 payload 过滤可占满；无锚时用融合榜首保底，并
保证 top-k 至少有一张事件卡）。这个反复调参的过程本身就是评测驱动的——见第 5 节。

### 3.4 rerank：召回宽、重排严

`bge-reranker-v2-m3` cross-encoder 对融合后的 top-20 逐对打相关性分，收敛到 top-5。
**召回阶段要宽（保证不漏），重排阶段要严（降低无关上下文带偏模型、还能省钱）**。在 Apple
Silicon 上重排约 10 对/秒（CPU 约 4 对/秒），单问 2–3 秒，可以接受。

## 4. 三个长在安全 domain 上的差异化功能

普通"知识库问答"供给已经过剩；真正值钱的是把 RAG 长在安全 domain 上。

### 4.1 拦截风险族归因

把一千多次 deny 用规则归并成风险族（外联 / 数据走私 / 越界写 / 进程命令 / fail-closed /
不可回滚 unknown）。脱敏后的分布：

| 风险族 | 占比（约） |
|---|---|
| 不可回滚 unknown（策略保守 / 可观测盲区） | **~75%** |
| 外联 | ~10% |
| 越界写 | ~8% |
| 进程命令 | ~7% |
| fail-closed | <1% |

最有价值的不是那张饼图，而是 **unknown 占约四分之三**这件事：它说明策略要么过度保守、要么
在大量事件上缺乏可读的归因——这是"从数据反推安全策略改进"的咨询级结论，而不是复述 reason。

### 4.2 绕行序列检测（代理人危机）

规则：`deny(工具A) → 短时间窗内出现同义调用(工具B)`，且**两侧都必须表达网络意图**（避免把
毫不相干的下一条命令误算成绕行）。真实命中（示意）：

- `curl <url>` 被拦 → 同一 URL 改用 `web_fetch`；
- `web_fetch <学术站点 pdf>` 被拦 → 改用脚本内 `urllib.request` 拉同一资源；
- `curl -A "Mozilla/…"` 伪装 UA 被拦 → 改走一个只读代理网关。

早期版本规则太宽，把"soffice 被拦 → 后来用了 web_search"也算成绕行（几十条噪声）。**加上
"双侧网络意图"这个约束后，信号从几十个收敛到十几个高置信**。RAG 在这里的作用是解释两次
行为的语义等价性，而不是靠规则硬判。

### 4.3 误拦代理：没有 ground truth，就设计测量闭环

真实误报率是算不出来的——你没有"这条到底该不该拦"的标准答案。所以我明确**不假装**能自动
算，而是做代理指标 + 人工确认：

- 同一实质动作（按"动词 + 目标"构造意图签名，如"安装某个 TTS 依赖包"）被拦后，N 分钟内换法
  成功 → 标记"疑似可策略优化"；典型如 `pip3 install <pkg>` 被拦 → `python -m pip install
  <pkg>` 成功。
- 问答页每张证据卡有 👍/👎，反馈写入**独立的** DuckDB，绝不改动审计数据。

> 误报率不能靠 LLM 算，只能设计测量流程；我做的是代理指标 + 人工确认闭环。

## 5. 评测驱动：有评测才叫工程，没评测只是演示

我建了 20 题黄金集（STATS / EVIDENCE / MIXED，**刻意含 2 道日志里根本没有答案的拒答题**，
比如反弹 shell、挖矿），每题标注应命中的证据 id 和答案要点。检索层对照（Recall@5，纯本地
跑出来）：

| 检索模式 | K=3 | K=5 | K=8 |
|---|---|---|---|
| 纯稠密向量（W2 风格） | 11% | **14%** | 14% |
| BM25 + 稠密 RRF（无 rerank） | 37% | **52%** | 52% |
| 混合 + rerank | 44% | **66%** | 66% |

三个能直接拿去面试讲的结论：

1. **混合检索相对纯稠密，Recall@5 从 ~14% 拉到 ~52%**，rerank 再拉到 **66%**——提升来自
   精确命令词和绕行序列，而不是玄学调参；
2. **K=5 是甜点**：K=3 漏召回，K=8 没有额外收益——这正是"召回宽、重排严、最终取 5"的
   量化依据；
3. 两道无答案题必须答"日志中未发现"，用**拒答正确率**量化反幻觉，而不是嘴上说"我会控幻觉"。

引用侧还有一道硬校验：模型输出的每个 evidence_id 必须**既在语料里真实存在、又在本题召回集
内**，否则判为非法引用。配合 STATS 数字原样透传，幻觉面被压到很小。

## 6. 技术栈为什么这么克制

- **DuckDB 而不是 Hadoop/数仓**：2.2 万行、单机、列存聚合秒级；按规模选型本身就是高级感；
- **Qdrant（docker compose，本地持久卷）而不是 Milvus 集群**：5.5k 向量不需要分布式；
- **内存 BM25 而不是 Elasticsearch**：零运维、tokenizer 可控；
- **本地 BGE-M3 + bge-reranker 而不是 API embedding**：无外发成本、无合规问题；
- **规则路由而不是再请一个 LLM 做 router**：分类确定、可复现、不增加一跳延迟和失败面。

每个"为什么不用"我都写进了 ADR（架构决策记录）。

## 7. 一句话总结

> 在安全分析场景，RAG 的价值不是"让模型答得多"，而是**让该确定的确定（SQL）、该精确的
> 精确（BM25）、该语义的语义（向量 + rerank）、该不知道就说不知道（拒答 + 引用校验）**，
> 再把这些能力长在"风险族归因 / 绕行检测 / 误拦闭环"这种真 domain 问题上。

这和权限门本身的 fail-closed 哲学是一致的：**宁可拒答，不可编造。**
