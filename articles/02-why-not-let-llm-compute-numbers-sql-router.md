# 为什么我不让大模型算数字：RAG 里的只读 SQL Router

> 本文数据均为**脱敏后的聚合统计**，不含真实用户名、主机路径、内网域名/IP 或邮箱；
> 全程本地运行，不连公网、不做公开部署。

## 1. 一个看似简单、实则危险的问题

安全分析台最常被问的问题之一是："**拦截率多少？**"

新手 RAG 的做法：把这个问题向量化 → 从库里捞几段最相似的文本 → 塞进 prompt → 让大模型
回答。模型可能会回："根据日志，拦截率约为 **5.2%** 左右。"

听起来没毛病。但追问三件事：

1. 这个数字**可复现**吗？同一个问题再问一次，temperature 波动一下会不会变成 5.4%？
2. 它**可审计**吗？是哪几条记录算出来的？分母是总调用还是总拦截？
3. 如果模型哪天回了 "**12%**"，你有任何机制能拦住它吗？

在 SOC/SIEM 场景，数字是要进周报、进处置决策的。一个会"合理地编造数字"的系统，比一个
老老实实说"我查一下数据库"的系统危险得多。

## 2. 核心原则：能确定回答的，绝不让模型自由生成

我把问题先过一个**确定性路由 Query Router**，分成三类：

| 路由 | 例子 | 走向 |
|---|---|---|
| **STATS** | "拦截率多少""越界写几起""fail-closed 几次" | 只读 SQL 取数，数字**原样**给模型，模型只组织语言 |
| **EVIDENCE** | "curl 为什么被拦""有没有绕行" | BM25 + 稠密混合检索 + rerank |
| **MIXED** | "一共拦了多少起，举几个网络拦截的例子" | 先取数、再检索，两路合并 |

Router 用的是**规则，不是另一个模型**。原因很朴素：

- 分类信号是关键词级的（"多少/几起/占比/率" vs "为什么/有没有/场景"），规则足够准；
- 不增加一跳 LLM 延迟、不引入第二个失败点、不花 token；
- 行为**可复现**：同样的问题永远走同一条路。

```
用户问题
   │
   ▼
规则 Router（不调模型）
   ├─ STATS ─▶ 受保护只读 SQL ─▶ 数字 ─┐
   ├─ EVIDENCE ─▶ 混合检索 ─▶ 证据 ───┤─▶ LLM 只做语言组织（不生产数字/id）
   └─ MIXED ─▶ 取数 + 检索 ─▶ 两者 ───┘
```

## 3. 但"让模型写 SQL"本身就是攻击面——所以加三道闸

完全写死常见统计当然最安全，但用户的问法千变万化，需要一定的 text2SQL 能力。
自由文本→SQL 一旦放开，就是一个注入/越权入口。我的做法是**允许模型（或规则）产出
SELECT，但执行前过三道独立的闸**：

### 闸 1：解析闸——只允许单条只读语句

在 SQL 文本上做白名单：

- 只能是单条 `SELECT` / `WITH`；
- 拒绝多语句堆叠（`...; DROP ...`）、`INSERT/UPDATE/DELETE`、任何 DDL、
  `ATTACH/PRAGMA/COPY` 等；
- 任何非预期关键字直接拒绝，根本不送到数据库。

这是"**默认拒绝**"（deny by default），和安全产品的思路一致。

### 闸 2：沙箱闸——只读副本，物理上写不进去

即使解析闸漏了一条写语句，也让它**在数据库权限层**失败：

- 先把 DuckDB 文件**复制到临时目录**；
- 用 `read_only=True` 打开这个副本；
- 原始审计库从头到尾不会被这条连接触碰。

纵深防御：不指望单一检查永远正确，而是让后一层兜住前一层的失误。

### 闸 3：dry-run + 行限——能跑通且不会拖垮

- 先用 `LIMIT 0` 的临时视图做一次计划验证（语句合法、表/列存在）；
- 再以 `LIMIT max_rows+1` 有界执行，多出来的那一行用来标记"结果被截断"。

这样一条失控的 `SELECT` 既不会全表扫爆内存，也不可能返回无界结果。

```
模型/规则产出 SQL
   │
   ▼
[闸1 解析：仅 SELECT/WITH、单语句、白名单] ──拒──▶ 拒绝，不执行
   │ 通过
   ▼
[闸2 沙箱：临时副本 + read_only]  ──写操作──▶ DB 自身拒绝
   │ 通过
   ▼
[闸3 dry-run LIMIT 0 → 有界 SELECT LIMIT N+1]
   │
   ▼
结构化结果（列、行、是否截断）
```

## 4. 数字怎么用：原样透传，LLM 只做"翻译"

取数结果以一个 `<stats>` 块原样拼进 prompt，并对 STATS 类问题加一条硬指令：
"必须原样使用 `<stats>` 中的数字，用一句话组织，不要编造 `<stats>` 之外的数值。"

示意（数字为脱敏聚合值）：

```
<stats>
总事件=22002，allow=20863，deny=1139，拦截率=0.0518（5.18%）。
</stats>

<question>整体拦截率是多少？</question>
<instruction>STATS 类：原样使用 <stats> 数字组织一句话，不要编造其它数值。</instruction>
```

模型回："整体拦截率为 **5.18%**（拦截 1,139 次 / 共 22,002 次工具调用）。"

**数字来自确定性工具，模型只做表达**。这带来三个性质：可复现（同样输入同结果）、可审计
（数字背后是具体 SQL）、成本低（不用长上下文也能答对一个聚合值）。

对那些最高频的审计统计（拦截率、越界写、fail-closed、类别分布、事件总数），我甚至不让
text2SQL 参与，直接用一个确定性 `known_stats()` 函数返回——常见问法零生成、零风险；自由
SQL 只作为受控扩展。

## 5. 它怎么和 RAG 的反幻觉体系咬合

不让模型算数字只是四层反幻觉里的第一层：

1. **Router 分流**：STATS 直接只读 SQL，模型碰不到生成数字这一步；
2. **证据约束**：EVIDENCE 答案里每个结论必须挂一个 evidence_id；
3. **引用后验**：程序解析模型输出，引用的 id 必须**既真实存在、又在本题召回集内**，否则
   判非法；
4. **强制拒答**：证据不足只能输出"日志中未发现"——黄金集里专门放了 2 道日志里根本没有
   答案的题（反弹 shell、挖矿）来量化"拒答正确率"。

数值隔离（第 1 层）针对的是一种特别隐蔽的幻觉：模型不会乱编一个明显离谱的 id（容易被
抓到），但它会很自信地编一个"看起来很合理"的百分比（很难一眼识破）。

## 6. 常见反对意见，以及我的回应

**"规则 router 会不会太笨？"**
对"统计 vs 证据"这种关键词可分的任务，规则准确率足够，且确定性 > 花哨。真遇到模糊问法，
默认走 EVIDENCE（更安全：检索至少有证据约束），需要时 MIXED 兜底。模型 router 是后续可选
增强，而不是起点。

**"白名单 SQL 会不会拦掉正常分析？"**
会牺牲一部分表达力，这是有意的。审计助手的高频问题是已知的几个聚合；长尾自由分析可以
走单独的人工/BI 通道，而不是把一个可写连接塞给模型。

**"复制 DuckDB 副本不是多此一举吗？"**
文件只有几十 MB、复制毫秒级。用极小的成本换来"物理上不可能写坏审计库"，这笔交易很划算；
等数据量真上来，再换成带权限的只读连接视图即可，闸的接口不变。

## 7. 一句话总结

> **大模型擅长把确定的事实组织成可信的表达，不擅长凭空产生可信的事实。**
> 所以数字交给受三道闸保护的只读 SQL、精确匹配交给 BM25、规则能定的不调模型，LLM 只在
> 需要语义归因和表达的最后一跳出场。

这跟整个项目的 fail-closed 哲学是同一件事：**宁可少答、宁可走确定的慢路，也不编一个漂亮
的假数字。**
